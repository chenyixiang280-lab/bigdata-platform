# 数仓任务草稿规范

来源为原dw-sql-rules第4—5节，2026-10-27离线整理。以下约定用于准备新任务；目标引擎、库规范、调度参数和UI校验仍须按当前项目核验。它们不授权执行建表/写入，也不是已验证的创建接口合同。

## SQL说明和建表草稿

脚本头记录引擎、主题域、用途、创建人/日期、修改记录、来源表和目标表。创建人未知则保留待填，不虚构。字段给中文注释，派生指标说明过滤与计算口径，增量事实表注明分区对应的业务日期。

原项目新表约定包含中文表名、`dw_etl_time`（首次加载）及 `dw_last_update_time`（最近更新），采用字符dt/`yyyyMMdd`、Parquet/SNAPPY。先核目标表类型和平台标准再使用；不能把这些约定套成已有表结构，不能每次重跑都重置“首次加载”而仍称语义不变。

DDL和转换SQL分开提供。目标表、字段顺序/类型、静态分区值、写入范围与来源过滤逐项对齐。执行只读查询路径不接受DDL/DML。

## 重跑、调度与资源

- 历史规范优先使用对明确目标分区的 `INSERT OVERWRITE`，多段来源可用 `UNION ALL` 后统一写入；先证明覆盖范围及粒度正确，排除重复。该规范不授权覆盖原表；用户要求保留原表时另建过程/结果表。
- 幂等性需区分业务值与运行时间等审计值：相同输入重跑业务结果不重复、不遗漏，审计字段按其语义处理。不要只因写了overwrite便宣称验证通过。
- `${dt}`、`${dt1}`、`${dt2}` 是历史参数占位，参数替换、日期含义与依赖触发须现场确认。未替换的占位符不能提交运行。
- 大表尽早做分区/列裁剪和必要过滤，在不改变计算语义时先聚合再关联。只有有实际必要时才拆临时视图/中间表；创建、留存、清理各自遵守授权。
- 历史命名 `tmp_{正式表名}_{序号}` 与 `test_{正式表名}` 不足以证明当前保留/清理策略，不依名称承诺“不可清理”或“自动清理”。
- 依据实际规模考虑拆批、错峰和资源申请。旧“10亿行”只是审查提示，不是实测的当前配额；LIMIT也不能替代分区裁剪。

## 命名与排版

旧命名模板 `{分层}_{主题域}_{业务描述}_{周期}{全增量}{分区策略}` 可作为新表命名建议：stg/ods/dwd/dws/dim/ads分层，trans/inv/memb等主题域，d/m/h/q周期，f/i全量或增量，p/n分区或非分区。实际含义仍以结构和SQL为准。

字段常用前后缀：`is_`、`_code`、`_amt`、`_qty`、`_rate`、`_date`、`_time`。拉链候选字段 `active_start_date` / `active_end_date` / `active_flag`，具体结束值与有效值须确认，不只凭 `_z` 后缀推断。

新SQL延续既有可读风格：小写关键字、4空格缩进、字段逐行、关键指标注释、复杂逻辑分CTE；维护现有SQL时不做无关格式化。旧“表名≤35字符、任务名严格等于表名、表中文名必须以表结尾”没有本轮平台校验依据，只能作为历史建议，不阻断已验证的合法名称。
